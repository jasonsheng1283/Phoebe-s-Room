# WORKFLOW — 需求处理工作流

> 最近更新：2026-07-24  
> 同步规则：`.cursor/rules/rule.mdc`

## 需求处理工作流

### 第一步：主动提问

- 收到需求后，先分析完整性，针对不明确的部分提问。

### 第二步：复述需求

- 用自己的理解复述，等待确认。

### 第三步：制定计划

- 根据讨论和确认的结论，制定实现计划文档，并更新到 `docs/plan/` 文件夹中。
- 不同计划用不同文件名，格式：`YYYYMMDD_plan.md`（同日多个计划可追加后缀，如 `YYYYMMDD_plan_auth.md`）。
- **仅针对**改动影响面较大 / 新功能 / 重构 / 在 Plan 模式下讨论和确认的改动；其他小改动不需要制定计划。

### 第四步：等待许可

- 必须得到明确许可后才能开始执行。

### 第五步：开始开发

- 动手前先评估改动范围：列出本次需要修改的文件和影响的模块。
- 确保最小且最合理的改动，不修改与需求无关的代码。
- 如果改动会影响其他已有模块的行为，必须先告知用户并获得确认。
- 按照 `.cursor/rules/rule.mdc` 中的技术规范开发。

### 第六步：结果验收

- 开发完成后，分别从顶尖前端设计师和顶尖视觉交互设计师的视角来验收，并给出验收报告。
- 验收报告包括：
  - 是否存在问题/缺陷
  - 是否存在改进空间
- 验收报告需要包含明确的需要修改的点，并给出修改建议。
- 根据验收结果，询问用户并获得是否需要修改的确认；如果需要修改，则返回第三步重新开始。
- 如果验收通过，则进入第七步。

### 第七步：开发完成

- 开发完成后，同步更新功能列表 `docs/features.md`。
- 按照 `docs/prd/template.md` 的结构补充 / 更新 / 调整 PRD 文档（入口见 `docs/prd/prd.md`）。
- 同步更新 `docs/CHANGELOG.md`。
- 将开发过程中遇到的重复出现的 / 严重的 / 有普遍性的问题同步更新到 `docs/PITFALLS.md`。
- 更新实现计划文档 `docs/plan/YYYYMMDD_plan.md`。

---

## 禁止行为

- ❌ 不要未经许可就开始执行开发或大规模改动
- ❌ 不要跳过「复述需求 → 等待确认」直接写计划或写代码
- ❌ 不要修改与当前需求无关的代码「顺手重构」
- ❌ 不要在未评估影响面的情况下改动公共模块行为
- ❌ 不要把猜测当成已确认需求写入 PRD（未确认项须标注「待确认」）
- ❌ 不要遗漏文档同步：功能列表 / PRD / CHANGELOG / PITFALLS / 计划状态
- ❌ 不要在面向儿童场景中引入不合适的内容、诱导成瘾的设计或无边界开放式对话

## 上下文加载

收到新任务时，先读取：

1. `docs/BACKGROUND.md` — 理解产品定位
2. `docs/GLOSSARY.md` — 对齐术语
3. 本文件 `docs/WORKFLOW.md` — 遵守流程
4. `docs/features.md` — 功能现状

## 功能点列表更新

- 每次 demo 更新后，同步更新 `docs/features.md`。
- 实现过程中的新发现或新增功能点，需更新到 `docs/features.md`。
- 功能点状态变化时，更新状态并记录状态变更时间。
- 更新类型和标识：完成 ✅ / 已废弃 ❌ / 新功能 🆕 / 进行中 🔄

## PRD 文件更新

- 每次更新 PRD 后，将更新后的 PRD 文件路径更新到 `docs/prd/prd.md`。
- PRD 正文结构遵循 `docs/prd/template.md`。

## 讨论存档

- 重要需求讨论、方案比选、确认结论写入 `docs/discussions/YYYYMMDD_*.md`。
- 讨论结论若改变产品定位或术语，同步回写 `BACKGROUND.md` / `GLOSSARY.md`。
